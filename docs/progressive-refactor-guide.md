# StreamHub 渐进式改造教学文档

> 当前状态：阶段 0 已于 2026-09-14 通过 `go build ./...` 和 `go test ./...` 验收；当前仅开启阶段 1。

## 一、项目现状评估报告

### 1. 项目概况

StreamHub 是一个 Go + Gin + MySQL 的小型视频站，当前采用三个可执行服务：

- `api`：用户、登录、视频元数据、评论，并托管静态页面（8080）。
- `streamsever`：上传和播放视频文件（9000）。
- `scheduler`：记录并异步清理视频文件（9001）。
- `static`：原生 HTML/JavaScript 前端。
- `internal`：已经开始抽取配置、数据库连接、应用错误和 HTTP 错误中间件。

项目已经实现注册登录、视频上传与播放、视频列表、评论和删除链路的基本骨架，但当前工作区正处在“统一错误处理”迁移中途，无法完整编译。

### 2. 现有优点

1. 已按三个运行职责拆分程序入口，比把所有逻辑塞进一个 `main.go` 更容易理解服务边界。
2. SQL 使用 `?` 参数，而不是拼接用户输入，具备基本的 SQL 注入防护。
3. 多数数据库资源有 `defer Close()`，遍历结果后也检查了 `rows.Err()`。
4. 密码等数据库配置已改为环境变量读取，`.env` 被 `.gitignore` 排除且当前未被 Git 跟踪。
5. UUID 使用 `crypto/rand`，随机源选择正确。
6. 已开始建立 `internal/config`、`internal/dbconn`、`internal/errs`、`internal/httpx`，说明项目正在向共享基础设施收敛。
7. 有少量工作流测试和较丰富的历史改造文档，便于追踪学习过程。

### 3. 主要问题与风险

#### P0：当前立即阻塞

- `api/auth.go` 中的 `context.Error(err error)` 是非法 Go 语法。
- 三个旧 `response.go` 已删除，但约 40 个 `SendErrorResponse` / `SendNormalResponse` 调用尚未迁移。
- `scheduler/main.go` 错误地导入并初始化了 `api/dbops`，而 handler 使用的是 `scheduler/dbops`。
- 实测 `go test ./...` 失败；因此目前没有可信的可运行基线。
- `api/dbops` 的测试在数据库未初始化时直接调用全局 `dbConnection`，导致 nil pointer panic，而不是清晰地跳过或报告依赖缺失。

#### P1：安全与数据一致性风险

- 用户密码以明文存入数据库；数据库泄露会直接暴露用户密码。
- `streamsever` 将 URL 中的 `vid-id` 直接拼接到文件路径，上传、读取、删除链路均存在路径穿越风险，例如恶意的 `../`。
- 上传接口没有鉴权；知道地址的人可以写文件。
- CORS 允许任意来源，且系统把 session 放在 `localStorage`；若前端出现 XSS，令牌容易被窃取。
- 删除元数据后才用无超时的 `http.Get` 通知 scheduler；通知失败仍返回成功，可能留下孤儿文件。
- API 删除时，非所有者返回了“未认证”错误，语义应是“已认证但无权限”（403）。
- `sessions.TTL` 定义为 `VARCHAR(8)`，但毫秒时间戳约 13 位，真实写入可能失败或截断；代码还吞掉了 session 写库错误。
- 数据表缺少外键及必要索引，可能产生孤儿评论、孤儿视频记录，列表查询也会随数据增长变慢。

#### P1：潜在运行时 Bug

- `RetrieveSession` 查询 `user_name`，表结构实际列名为 `login_name`。
- `ListComments` 把评论 `id` 填进了 `VideoId` 字段。
- `ListAllVideos` 未关闭 `rows`。
- `IsSessionValid` 在 session 已存在但过期时不删除；反而在“不存在”时执行删除。
- 多处 `interface{}` 裸类型断言可能 panic。
- scheduler 的删除函数忽略绝大多数 `os.Remove` 错误，而且文件路径同样靠字符串拼接。
- scheduler runner 使用关闭 channel 后继续接收也无法区分状态；测试依赖 `Sleep(3s)`，慢且不稳定。
- 连接限制器使用“先看 `len` 再发送”的非原子操作，并发下仍可能阻塞。
- `ParseMultipartForm(50MB)` 不是完整的请求体硬上限，且没有检查文件类型。
- API 调 scheduler 没有超时，也没有校验对方 HTTP 状态码。

#### P2：结构与可维护性问题

- handler 同时负责 HTTP 解析、业务规则、数据库调用和跨服务 HTTP 调用，职责过多，难以单测。
- `dbops` 使用包级全局数据库变量，依赖隐式，测试和多实例初始化困难。
- 请求 DTO、数据库结果模型和响应模型混放在 `api/defs`，边界不清晰。
- 错误响应目前存在新旧两套模型，响应契约不稳定。
- 命名未遵循 Go 常用缩写规则：`Id`/`SessionId`/`AuthorId` 宜逐步统一为 `ID`/`SessionID`/`AuthorID`；`streamsever` 还存在拼写问题，但不应现在贸然改目录。
- 前端存在端口 `9000` 与 `9090` 混用、模板字符串写成 `$(vid)` 等明显问题，并有重复上传逻辑。
- README 只有标题，缺少启动方式、环境变量、端口和架构说明。

### 4. 改造前后的方向对比

| 维度 | 当前方式 | 渐进目标 |
| --- | --- | --- |
| 依赖 | 包级全局变量、handler 直接调用 | 构造时显式传入，小范围接口隔离 |
| 错误 | 各服务各自响应、部分错误被吞 | 业务错误向上返回，统一在 HTTP 边界转换 |
| 安全 | 明文密码、路径直接拼接 | 密码哈希、路径校验、上传鉴权 |
| 测试 | 依赖真实全局 DB、Sleep 等待 | 可替换依赖、确定性单元测试、少量集成测试 |
| 配置 | 已部分集中 | 端口、目录、跨服务地址统一进入配置 |
| 前端 | 单文件脚本、硬编码地址 | 先修契约和 Bug，再渐进拆分模块 |

## 二、分阶段路线（暂不展开后续任务）

每个阶段只设一个核心学习目标：

0. **恢复可信基线**：学会用编译器、格式化和测试建立反馈闭环。（当前阶段）
1. **统一一个服务的错误边界**：只迁移 API，不同时改三个服务。
2. **输入与路径安全**：阻断路径穿越，理解“不信任外部输入”。
3. **密码安全**：引入密码哈希，理解哈希与加密的区别。
4. **会话生命周期**：修复持久化、过期与错误传播。
5. **显式依赖**：先对一个小模块移除全局数据库依赖。
6. **业务层分离**：从一个 handler 提取 service，学习职责分层。
7. **跨服务调用可靠性**：封装 scheduler client，加入超时和状态检查。
8. **调度器并发模型**：修 channel、错误传播和确定性测试。
9. **数据模型与数据库约束**：统一命名、时间类型、外键和索引。
10. **前端契约与模块化**：集中请求函数，消除硬编码和重复逻辑。
11. **工程收尾**：README、日志、健康检查、优雅停机与部署准备。

阶段顺序可以根据实际 Bug 调整，但一次只开启一个阶段。

## 三、当前阶段 0：恢复可信的编译基线

### 阶段目标

不做业务重构，不改变接口行为，只让当前中断的迁移回到“小步可验证”的状态。完成后，三个程序包至少能通过编译；需要真实 MySQL 的测试要能明确说明前置条件，而不能 panic。

### 核心知识点：反馈闭环

工程化的第一步不是分很多层，而是让每次修改都能快速回答三个问题：

1. 代码语法是否合法？——由编译器回答。
2. 代码是否符合 Go 的标准格式？——由 `gofmt` 回答。
3. 旧行为有没有被破坏？——由测试回答。

这三项构成“反馈闭环”：修改越小，报错与修改之间的因果关系越清楚。当前一次同时删除三套响应 helper、接入新中间件并改调用点，跨度较大，所以出现了大量编译错误，定位成本也随之上升。

`context.Error(...)` 的含义是把一个已有的 `error` 挂到 Gin 请求上下文，让请求结束后的错误中间件统一转换成 HTTP 响应。参数必须是一个错误值，例如 `errs.Unauthorized("...")`，`err error` 则是函数参数声明语法，不能出现在调用表达式里。

### 【必做基础任务】

#### 任务 1：先保存当前迁移边界

查看 `git diff`，用自己的话记录：哪些文件是新增、删除、修改；不要直接清空或覆盖当前工作区。建议为这次中间状态创建一个普通 Git 提交或至少保留 diff 补丁，但是否提交由你决定。

#### 任务 2：修复两个独立的编译错误

1. 在 `api/auth.go`：
   - 删除没有被使用的 `defs` 导入。
   - 引入共享的 `internal/errs`。
   - 当用户名为空时，把一个 `Unauthorized` 错误交给 `context.Error(...)`。
   - 注意：这里先只修编译与错误传递，不改函数签名。
2. 在 `scheduler/main.go`：
   - 把错误的 `api/dbops` 导入改成 `scheduler/dbops`。

每改完一个文件立即执行 `gofmt -w <文件>`，然后运行针对性命令：

```bash

go test ./scheduler
```

它们仍可能因响应 helper 缺失而失败，这是预期的；重点是确认原来的语法错误和错误包初始化问题已经消失。

#### 任务 3：用“兼容层”暂时恢复三个服务的编译

不要在本阶段迁移约 40 个 handler 调用。把 Git 中删除的三份旧 `response.go` 恢复回来，明确把它们视为临时兼容层。新错误中间件可以先保留，它只处理 `context.Error(...)` 收集到的错误；旧 helper 仍直接写响应，两者在单个请求中不要同时使用。

为什么允许临时重复？因为当前阶段的唯一目标是恢复基线。下一阶段会只迁移一个服务，并在该服务迁完后删除对应兼容层。这样每一步都可编译，也容易回退。

恢复后运行：

```bash
gofmt -w api scheduler streamsever internal
go build ./...
```

### 代码修改指引（不是完整答案）

错误传递应形成以下方向：

```text
ValidateUser 发现未认证
    -> 创建一个 Unauthorized 类型的应用错误
    -> context.Error(错误值)
    -> 请求返回后 ErrorHandler 读取 c.Errors
    -> 转成 401 JSON
```

scheduler 的数据库初始化必须和它自己的 handler 使用同一个包级连接：

```text
scheduler/main.go 初始化 scheduler/dbops
                         |
scheduler/handlers.go 使用 scheduler/dbops
```

如果两边导入不同包，即使函数都叫 `Init`，也是两个完全不同的包级变量。

### 关键注意事项

- 不要修改 `.env`，也不要把密码贴到提交或聊天中。
- 不要顺手修复所有 handler；范围扩大后将无法判断是哪一步破坏了行为。
- 不要删除现有 `internal/httpx` 和 `internal/errs`，它们是下一阶段的学习对象。
- 不要为了让测试变绿而忽略所有错误或移除测试。
- 恢复兼容文件时要以 Git 中原内容为准，不凭记忆重写。
- `gofmt` 只做格式化，不证明逻辑正确。
